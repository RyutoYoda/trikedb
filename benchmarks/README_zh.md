# 基准测试

按重要程度排序的两个问题：

1. **[图谱能让 LLM 更准确吗？](#kgqa-图谱能减少幻觉吗)**
   — 在 300 道 WebQSP 问题上 Hits@1 从 42.7% 到 77.7%，两边用的是同一个模型。
   我们同时报告评分协议本身的敏感性，因为标题数字会随着你怎么评分而变动。
2. **[天花板在哪里？](#天花板在哪里)** — 哪个操作最先变得不可用，以及在多大的
   图谱规模上。这和「能装多少条三元组」是两个问题，而后者根本没有东西能碰到。

## KGQA：图谱能减少幻觉吗

**问题：** 当一个 LLM 以 trikedb 图谱作为上下文来回答事实性问题时，它比同一个
LLM 独自作答准确多少。

**设置：** 从完整的 1,628 题 [WebQSP](https://aclanthology.org/P16-2033/) 测试集里
抽样 300 题（seed 42），经由 [RoG-WebQSP](https://huggingface.co/datasets/rmanluo/RoG-webqsp)
重打包版 — 每题都带标准答案和一个 Freebase 子图，运行时下载，本仓库不存储任何
数据集内容。每个子图被载入一个内存中的 TrikeDB（中位数 5,088 条三元组），每题的
上下文用 trikedb 自己的 `search()` 和 `find()` 检索：以问题实体的邻域为锚，加上
按语义排序的事实，上限 250 条三元组。阅读模型是经由 Ollama 的 `qwen3:8b`，
temperature 0。Hits@1 和 F1 按 RoG 参考实现的算法计算。

**结果**（n=300，两个条件都回答了全部问题）：

| 条件 | Hits@1 | F1 |
|---|---|---|
| 模型单独作答 | 42.7% | 27.9% |
| **模型 + 一个 trikedb 图谱** | **77.7%** | **57.4%** |
| 差值 | **+35.0pt** | **+29.6pt** |

![按条件划分的 Hits@1 与 F1](accuracy.png)

同一个模型，同一个提示，同一批问题。唯一变化的是检索到的三元组是否在上下文里。

值得放在旁边一起看的两个数字：

|  | 答对了 | 没答对 | 合计 |
|---|---|---|---|
| 检索够到了答案 | 230 | 38 | 268 |
| 没够到 | 3 | 29 | 32 |
| 合计 | **233** | 67 | 300 |

请纵向读这张表，而不是横向读标题：

- **剩下的差距在哪里。** 有 38 题答案就坐在上下文里，而模型没把它说出来。这是
  阅读模型的问题，不是图谱的问题 — 而它值 12.7 个百分点，所以在同样的检索上换
  一个完美的阅读模型就是 89.3%。
- **检索的够到率和准确率是两个不同的量。** 89.3% 的题目答案在上下文里；77.7%
  产出了正确答案。在够到的那部分里，模型转化了 **85.8%**（268 中的 230）。用两个
  比率相除（77.7 / 89.3 = 87%）得到的不是这个数字，而且没有任何意义 — 条件概率
  必须去数。
- **在这里模型靠自己几乎没有贡献。** 没够到的 32 题里，只有 3 题是模型凭自己已有
  的知识答对的。检索更弱的时候要多得多：在 1-hop + CVT 那一轮里，有 24 个正确答案
  来自检索漏掉的题目。更好的检索不只是增加正确答案，它还接手了原本靠模型记忆
  扛着的那些。

**300 题够吗？** 已发表的数字是在全部 1,628 题上算的，所以要检查两件事：区间，
和样本。

| | Hits@1 | Wilson 95% 置信区间 |
|---|---|---|
| 模型单独作答 | 42.7% | 37.2 – 48.3 |
| 模型 + 图谱 | 77.7% | 72.6 – 82.0 |

两个区间不重叠 — 48.3 低于 72.6 — 所以 35 个百分点的差距不是 300 题的样本靠运气
能造出来的。每个单独的数字大约带 ±5 个百分点，这正是应该读差值而不是读绝对分数
的理由。

这个样本（seed 42）在所有会让题目变简单的维度上都与全集一致：标准答案数中位数
2 对 2，子图中位数 4,588 条三元组对 4,415，问题长度中位数 7 个词对 7 个。它在一个
维度上*更难* — 标准答案数均值 13.0 对 10.2，多答案题目的尾部更重 — 这对 F1 是
不利的，不是有利的。

**复现：**

```bash
uv run --extra all --with polars --with model2vec \
    python benchmarks/webqsp_bench.py prepare --n 300 --seed 42 \
    --retrieval "hybrid (entity + semantic)" --cap 250 --out bench_out/hybrid

for cond in nograph graph; do
  uv run --extra all --with polars python benchmarks/webqsp_bench.py run \
      bench_out/hybrid/eval_set.json --model qwen3:8b --condition $cond \
      --style grounded --out bench_out/ans_$cond.jsonl --workers 8
done

uv run --extra all python benchmarks/webqsp_bench.py score \
    bench_out/hybrid/eval_set.json bench_out/ans_*.jsonl \
    --json benchmarks/accuracy_data.json
```

模型是本地的、并且写明名字，这是有意为之：分数取决于模型，所以读到这个数字的人
必须能重跑它。藏在付费端点后面的一个 API key 既不可指名，也不稳定。

**需要说明的保留。** 包含匹配很宽松，但对两个条件同样宽松。WebQSP 的标准答案有
噪声（见下文），这为诚实的绝对分数设了上限。阅读模型是一个 8B 的开源模型在做
零样本作答 — 在比较之前请先读
[已发表数字处于什么位置](#已发表数字处于什么位置)。同一套设置在 30 题上用
`claude-haiku-4-5` 做的早期试点，在朴素的包含协议下得到 60% → 83%；它已被上面
那张表取代，后者用了十倍的题量和一个任何人都能跑的模型。

## 检索方法值多少

检索层之上的一切都被固定住了 — 同样的 300 题，同样的模型，同样的提示，
**同样的 250 条三元组预算** — 所以唯一的变量是*哪* 250 条被选中：

| 检索 | 答案在上下文中的比例 |
|---|---|
| 1-hop + CVT（这个基准测试此前一直用的） | 212/300 · 70.7% |
| **hybrid — 实体锚点 + `search()` 排序** | **268/300 · 89.3%** |

上下文的量一样，其中有用的部分多了 18.6 个百分点。这个数字是对全部 300 题的
计数，不是估计。

它买到的准确率，在两轮都回答了的题目上检验：

| 检索 | Hits@1 | n |
|---|---|---|
| 1-hop + CVT | 68.6% | 245 |
| hybrid | 77.7% | 300 |

配对来看，hybrid 在对方答错的 36 题上答对，在对方答对的 19 题上答错 — 精确
McNemar 检验 **p = 0.03**。是真的，但离图谱对无图谱的结果（125 比 20，
p = 9e-20）还很远，值得当作两个主张里较弱的那一个。

关于这是怎么检验的需要说一句，因为在这里那个看似显然的做法是错的。这些轮次是用
*同一个*模型回答*同一批*问题，所以配对本身就是关键；比较它们的两个 Wilson 区间
（62.5–74.1 对 72.6–82.0）会仅仅因为区间相接就让差异看起来没有定论。`compare`
改为做配对检验 — 只有两轮意见不一致的题目携带信息，而要问的是那个分裂有多不
对称。

检索用的是 trikedb 自己的 `search()` 和 `find()`，比较的框架是
`retrieval_bench.py` — `webqsp_bench.py` 从它那里 import 这些方法，而不是自己留
第二份拷贝，因为检索的数字正是用来解释准确率数字的。

**倒进去更多不是杠杆，选得更好才是。** 取消上下文上限（见下文）让每一个标准
答案都变得可达，而准确率没有动。

**实体锚点只在预算大的时候才值回本钱。** 在更小的上限上重建，hybrid 和纯语义
检索无法区分：

| 检索 | 上限 | 答案在上下文中 |
|---|---|---|
| hybrid | 250 | 89.3% |
| hybrid | 150 | 84.7% |
| 语义检索 | 150 | 84.7% |
| 语义检索 | 100 | 81.7% |
| hybrid | 100 | 81.3% |

在 150 条时两者完全打平，而在 100 条时锚点是一个轻微的*损失*。把一份小预算的
一半花在保证问题自身的实体上，就是那一半没有花在排序上，而找到答案靠的是排序。

## 更小的上下文够吗

250 条三元组的上下文占了运行时间的大部分，所以显而易见的问题是：便宜一点的行不
行。用纯语义排序在 100 条三元组上重建 — 可达率 81.7% 对 89.3%，提示不到一半长：

| 条件 | Hits@1 | F1 | n |
|---|---|---|---|
| 无图谱 | 42.7% | 27.9% | 300 |
| 图谱 · 语义检索，100 条 | 70.3% | 52.6% | 300 |
| 图谱 · hybrid，250 条 | **77.7%** | **57.4%** | 300 |

不够 — 而这是一个测出来的答案，不是一个假设。配对来看，250 条的配置在 100 条那
一版漏掉的 34 题上答对，在它答对的 12 题上答错，精确 McNemar 检验 **p = 0.002**。
多出来的上下文挣回了它的延迟。

之所以值得写出来，是因为这条曲线的形状在被测量之前被猜错了：既然试点里取消上限
没有帮助，那预期就是收益会在 250 以下某处递减，而小上下文近乎免费。实际上收益在
250 处仍在攀升。「更多上下文没有帮助」和「更少上下文也没关系」是两个不同的主张，
而被检验过的只有前一个。

## 上下文的代价

在你自己跑之前值得知道：墙钟时间几乎全部是**提示的 prefill**，不是生成。答案很短
— 中位数两行 — 所以运行时间取决于模型每题必须读多少个上下文 token。

| 条件 | 提示 | 300 题 |
|---|---|---|
| 无图谱 | 约 120 token | **7 分钟**（实测） |
| 图谱，250 条三元组 | 约 5,400 token | 约 60 分钟（实测） |

这个比例正是上面那张检索表值双份重视的原因：一个用更少三元组达到同样够到率的
方法，同时也快好几倍。并发不是解决办法 — GPU 已经被 prefill 打满了，把
`OLLAMA_NUM_PARALLEL` 提到 8 并用 `--workers 8`，收益远小于减少 token 数带来的
收益。`--workers` 仍然保留，因为在无图谱条件下它是免费的，而且在 prefill 不是
瓶颈的机器上它有效。

## 图谱值得它带来的延迟吗

图谱花的是提示 token，而提示 token 就是运行时间。在一台空闲的机器上单独测量，
一次一个请求 — 这是一个只问一个问题的人真正要等的延迟：

![准确率对每题秒数](frontier.png)

| 条件 | 秒数中位数 | 提示 | Hits@1 |
|---|---|---|---|
| 无图谱 | 0.47 | 约 56 token | 42.7% |
| 图谱 · 语义检索，100 条 | 9.44 | 约 1,823 token | 70.3% |
| 图谱 · hybrid，250 条 | 22.48 | 约 4,377 token | 77.7% |

头 9 秒买来 27.6 个百分点。接下来的 13 秒再买 7.4 个，而配对检验说这是真的
（p = 0.002）— 所以曲线在它停下的地方仍在攀升，这里并没有找到「再多上下文就不
划算」的那个点。

这些是有意采用的单请求数字。批量运行时记录的每题延迟要高得多 — 100 条配置的
中位数是 31.7 秒 — 因为当时有八个请求同时在飞，每个都在别人后面排队。那个数字
对规划吞吐是对的，对「多久能看到答案」是错的，所以两者分开保存。

## 这里面哪一部分是 trikedb

值得分开说，因为这条流水线的两半在这里是分别测量的，而它们的极限并不相同。

**trikedb 的工作是把答案摆到模型面前。** 在这 300 题上它做到了 **89.3%**，而这
份工作每题耗时 **0.59 秒** — 把整个 4,640 条三元组的子图构建成一个图（几乎是
瞬时的），并在它之上跑 hybrid 检索。这是一题端到端 22.5 秒里的 2.6%；另外
21.9 秒是模型在读上下文。没有服务器，没有要构建的索引，没有第二份存储：只是在
一份文档上做 `search()` 和 `find()`。

**模型的工作是把它变成答案**，而不够的正是这一半。它转化了递给它的 85.8%，并且
丢掉了 38 道答案就在眼前的题 — 占总量的 12.7 个百分点。

| | 够到 / 转化 | 每题时间 |
|---|---|---|
| trikedb — 找到事实 | 89.3% 的题目 | 0.59 秒 |
| `qwen3:8b` — 使用它们 | 其中的 85.8% | 21.9 秒 |
| 端到端 | **77.7%** | 22.5 秒 |

由此得出两点，而且都值得直说：

- **检索这一侧不是瓶颈，而且它改进了很多。** 仅仅替换检索方法，就在完全相同的
  上下文预算下把够到率从 70.7% 提到 89.3%，用的只有 trikedb 自己的原语。89.3%
  落在已发表方法在这个基准上端到端报告的区间之内 — 上限不是分数，但它确实意味
  着：被供给的事实不是压住这个数字的原因。
- **端到端的数字跟着阅读模型走。** 77.7% 是一个 8B 开源模型零样本面对这份上下文
  给出的结果。已发表的领先者跑的是 GPT-4 级或针对任务微调过的阅读模型，而那
  38 道被丢掉的题正是更强的阅读模型会得分的地方。换阅读模型只是改一个参数
  （`--model`），而把这两半保持可分离，目的就在这里。

## 已发表数字处于什么位置

已发表的 WebQSP 领先者报告的 Hits@1 在 80 多的中段到高段，F1 在 70 左右。这里
引用的唯一一个数字，是那个可以核对、并且这套框架正是照着它建的：
[RoG](https://arxiv.org/abs/2310.01061)（ICLR 2024）在 WebQSP 上用一个微调过的
LLaMA-2-7B 阅读模型报告 **F1 70.8**，而它的指标实现正是 `score` 所复现的。

那份榜单上的其他数字被刻意*没有*列成表格。它们很容易被抄错 — 同一个方法会因为
数据划分、检索器、以及阅读模型是否经过微调，在不同论文里以不同的数字出现 —
而把一张未经核实的数字表放在你自己的数字旁边，比没有表更糟。

拿它们和上面的数字对读时真正要紧的：

- **阅读模型。** 领先者跑的是 GPT-4 级或针对任务微调过的模型。这个基准测试在一台
  笔记本上跑一个 8B 的开源模型做零样本，并写明它的名字，所以这个数字不需要
  API key 就能复现。
- **协议。** 这一部分*是*可比的：Hits@1 和 F1 按 RoG 参考实现的算法计算 — 归一
  化，去掉冠词和标点，做子串匹配，每个标准答案只记一次。偏离它会得到一个看起来
  可比、实际上不可比的数字，这也是 `_normalize` 和 `f1` 在源码里带着那段说明的
  原因。

## 评分敏感性（为什么我们报告包含协议）

*本节和下一节的所有数字都来自早先那次 30 题、使用 `claude-haiku-4-5` 的试点，
而不是上面那张 300 题的表。保留它们，是因为它们关于协议所说的仍然成立，也因为
那些发现正是导向上面检索工作的原因。*

为了透明，三种评分变体：

| 协议 | LLM 单独 | LLM + 图谱 | 差值 |
|---|---|---|---|
| 包含匹配（主要） | 60% | **83%** | **+23pt** |
| 包含，检索 v2（按相关性排序的上下文） | — | 77% | — |
| 包含，检索 v3（更深的 CVT 展开） | — | 80% | — |
| LLM 评审，以标准答案为锚，对两个条件都适用 | 73% | 77% | +4pt |

在你自己调这个基准之前值得知道的发现：

- **按相关性给上下文排序反而有害。** 按问题词重叠度给三元组排序，在若干题目里把
  真正含答案的三元组挤出了上下文上限（例如 GDP 计量的 `currency` 三元组排在了
  那个国家真正的货币之前）。朴素的按跳数顺序检索表现更好。
- **标准答案有噪声。** 抽样题目里约 10% 的标准答案是可疑的（例如「二战期间的
  苏联领导人」→ 标准答案是*勃列日涅夫/赫鲁晓夫*；「伽利略做了什么而成名」→
  标准答案是一串职业）。这为在原始 WebQSP 标签上诚实的绝对分数设了上限 — 已发表
  的 SOTA 停在约 86% 附近也是同一个原因。
- **用 LLM 当评审来打分是不稳定的。** 一个接受粒度差异的评审会救回无图谱条件下
  那些含糊的回答并压缩差值；一个更严格的评审又会把差值还回来。因此我们把确定性
  的包含协议作为主要口径 — 它可以从已提交的脚本复现，没有任何需要判断的地方。

稳健的主张是那个**差值**：在任何一个对两个条件同等适用的固定协议下，图谱条件都
胜出。在原始 WebQSP 标签上诚实地达到 90% 以上的绝对分数是做不到的（标签噪声）；
一个在自包含 KB 上的一跳基准（例如 MetaQA 1-hop，目前在 HF 上是受限的）才是追求
高绝对值该瞄的目标。

## 检索深度实验（更多上下文有帮助吗）

在同一批 30 道试点题上的后续实验。这一节正是后来变成上面那部分检索工作的起点：
它确立了*更多*上下文不是杠杆，所以修正的做法是选得更好的 250 条三元组，而不是
更大的上限。

| 检索 | 答案可达上限 | 准确率 |
|---|---|---|
| 1-hop + CVT，上限 250（v1） | 20/30 | **83%** |
| 更深的 CVT 展开，上限 400（v3） | 23/30 | 80% |
| 同上，**不设上限**（中位数 912 条/题） | **30/30** | 80% |
| + OWL-RL 传递性物化（19,070 条推导事实） | 23/30 | 未重跑 |

两个值得内化的发现：

- **可达性不等于准确率。** 去掉上下文上限让每一个标准答案都变得可达（30/30），
  但准确率没有提升：当每题约有 900 条三元组时，模型开始从这片洪水里挑出「看起来
  合理但是错」的条目（一部电视剧而不是电影，一首无名的歌而不是那些著名的）。
  瓶颈从检索移到了注意力。修正的办法不是倒进去更多，而是*迭代式*检索 — 让智能体
  通过 MCP 一轮一轮地查询图谱。
- **推理是正交的。** 对地点类谓词物化传递闭包增加了 19,070 条正确事实，却没有让
  任何一个额外的答案变得可达：WebQSP 的多跳问题是通过中介节点串起*不同的*谓词，
  没有哪条 OWL 公理能把它缩短。OWL 值回本钱的地方是同一谓词的链条（角色继承、
  包含层级），而不是这个基准。

在任何深度下剩余的失败，主要由标准答案噪声（4/30）和答案粒度不匹配主导 — 这与
已发表 SOTA 在 80 多的中段趋于平缓是一致的。

## 天花板在哪里

**问题：** 一个图谱能长到多大，同时还是那种你放在 git 里、在 pull request 里
审阅、查询时不用等的图谱。

一份文档*能装下*的规模，结果是最没意思的那个答案。按下面测量结果外推，每条
三元组大约 58 字节、3 KB 内存：

| 限制 | 三元组数 | 是否为约束 |
|---|---|---|
| 8 GB 内存 | 约 2,500,000 | 不是 — 你会先撞上其他所有东西 |
| GitHub 的 100 MB 文件阻断 | 约 1,700,000 | 不是 |
| GitHub 的 50 MB 文件警告 | **约 870,000** | 硬停止点，而且没有东西能到达它 |

任何经过整理的东西都不会接近 870,000。它真正被用于的那些图谱 — 一张运维地图、
一份领域本体、一个聊天机器人的知识库 — 都在那个数字之下两到三个数量级运行。
所以「能装多少条三元组」不是那个值得回答的问题。

**你真正会撞上的，是一个个功能逐一变慢，而且它们不是同步退化的。**

![每个操作都撞上它自己的天花板](ceiling.png)

语义检索在 1 万条三元组时离开队伍，到 3 万条就不可用了，而对同一个图谱的 SPARQL
在 20 万条时仍在四分之一秒内给出答案。读和写落在中间，而*你选了哪种格式*会把
它们挪动一个数量级。

| 三元组 | YAML | 打开 `.json` | 打开 `.yaml` | 保存 `.yaml` | SPARQL 两跳 | `to_html` | HTML | `search()` |
|---|---|---|---|---|---|---|---|---|
| 733 | 0.0 MB | 1 ms | 9 ms | 8 ms | 1 ms | 14 ms | 0.2 MB | 19 ms |
| 2,040 | 0.1 MB | 1 ms | 35 ms | 26 ms | 2 ms | 39 ms | 0.5 MB | 42 ms |
| 7,333 | 0.4 MB | 5 ms | 122 ms | 101 ms | 9 ms | 163 ms | 1.7 MB | 155 ms |
| 20,400 | 1.1 MB | 13 ms | 456 ms | 305 ms | 26 ms | 491 ms | 4.8 MB | 4.3 s |
| 73,333 | 3.9 MB | 71 ms | 1.6 s | 1.0 s | 94 ms | 1.9 s | 16.9 MB | 13.5 s |
| 204,000 | 11.2 MB | 147 ms | 4.6 s | 3.2 s | 297 ms | 6.0 s | 48.9 MB | 41.9 s |

这些数据由 `ceiling_bench.py` 产出；`ceiling_chart.py` 从它的 JSON 画图。在一台
Apple silicon 笔记本上三次取中位数，一个流水线形状的合成图谱（供应商 → 作业 →
表，三分之一的边带 note/prov 属性）。绝对数字在你的硬件上会不同；要点是每条曲线
的*形状*。

### 怎么读

**到约 1,000 条三元组。** 一切都是即时的，而且你可以在一个 pull request 里审阅
整个图谱。这就是这个工具为之成形的规模。

**到约 10,000 条。** 各处仍然舒适，包括语义检索（155 ms）。审阅整个图谱在这附近
不再现实 — 1 万条三元组就是 1 万行 — 所以审阅转向 diff。一条事实的改动在*任何*
规模下都是一行 diff，所以那条路可以无限期地走下去。

**到约 100,000 条。** SPARQL 和模式查询仍然很快（两跳连接 93 ms）。有三件事不再
令人愉快：语义检索（13 秒）、HTML 工作台（生成 1.9 秒，在浏览器里打开 17 MB），
以及以 YAML 保存（1.1 秒 — 在默认的 `autosave=True` 下这是*每一次* `add()` 的
代价；改用 `autosave=False` 打开并批量处理）。把文件命名为 `.json` 能让打开和保存
都便宜一个数量级。

**超过约 500,000 条。** 它能工作，但已经在这个设计的适用范围之外。保存要好几秒，
git 在搬一个 20 MB 的文本文件，而 GitHub 不再渲染 diff。

### 什么*不会*退化

- **一次改动的 diff。** 在 700 条和 70 万条三元组上都是一行 — 因为三元组一行一条
  地序列化，而保存是确定性的。
- **按后端划分的查询。** 一个 `snowflake://` 行、一个 `s3://` 对象和一个本地文件
  用同样的时间回答同一个查询；图谱是从内存里回答的，所以后端只决定打开和保存的
  代价。参见 `backend_bench.py`。
- **构建图谱。** `add()` 在 0.27.0 之前是 O(n²) — 用于 upsert 检查的线性扫描让
  10 万条三元组的构建耗时 289 秒，单次 `add` 的代价从 60 µs 涨到 2.9 ms。现在它
  建了索引，所以导入一个大图谱是线性的。加载从未受影响。
